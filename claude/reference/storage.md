# Storage

These rules are part of the global instructions (`~/.claude/CLAUDE.md`, Storage section) and have the same force. Read them before you use `storagectl` or split work across machines.

- Keep work that another machine or a later session may read on the shared storage through `storagectl`, not only in a local folder: downloads, datasets, run outputs and handoff files. Start with `storagectl dests` to see which destinations are online, then use `put`, `get`, `ls`, `find`, `fetch <url> <dest>:<path>/` or `run --to <dest>:<path> -- <command>`. The commands, and how a service requests its own allocation, are in `docs/storage/README.md` in syz51/vps.
- Choose the destination by need: `cloud` (Tencent COS; always reachable, deleted files recoverable for 30 days) or `sai` (12 GiB) when the data must not depend on a Mac being awake; `pro` for large data, offline while the Pro sleeps; `air` (small) only for work in progress, never for an archive; `svps` for small results only, since its uploads are slow. On sai and svps, `storagectl` works only in root login shells. Finished work that is kept (archives, parked task scratch, outputs of a closed study) goes to `cloud:archive/<repository name>/`, not to `air`; large data still goes to `pro`. A project rule against disclosure to external services, such as the one in masters, does not forbid this: these destinations are my own storage. A project rule that keeps named material on one machine or out of third-party storage still applies, and credentials stay out.
- Split work across machines when another one suits a step better: `sai` for large downloads and COS-heavy steps, the Pro for large data and long CPU jobs. From the Air or the Pro, run such a step with `storagectl run --on sai|pro --to <dest>:<path> [--stage <file or dir>] -- <command>`. It runs detached as that machine's `storage-runner` account and prints a job id; the command writes results to `$STORAGE_OUT`, which is sent to `--to` with the job's log, also when it fails. Follow it with `storagectl status|logs|cancel <id>` or `storagectl jobs --on <machine>`. Stage only small inputs (up to 1 GiB); pass larger ones through destinations, which the job reads with `storagectl` and the runner's own keys. sai jobs get one CPU and 768 MiB and cannot reach local or tailnet services other than the storage pools. Never run workloads as root on sai or svps; svps runs no jobs.
- To run a full T3 thread on the Pro from the Air (while the Pro is awake), check `t3_environment_links` for its `environmentId`, then call `delegate_task` targeting that `environmentId` on `antigravity` (`gemini-4-neon`, omitting `isolation: "worktree"`) and exchange inputs and outputs through `storagectl`. To read threads on the other Mac, pass its `environmentId` to `t3_thread_list` or `t3_thread_read` (Air → Pro is `full-access`; Pro → Air is `read-only`). To check the Pro's `~/.config` commit read-only as the Pro's user, run `git -C ~/.config log -1` over SSH to the Pro host in `~/.ssh/config.d/` or in a Pro T3 thread (`storagectl run --on pro` runs as `storage-runner` and cannot read it). The Pro's providers, repositories and reach are in `docs/storage/README.md` in syz51/vps.
- Report what got in the way as Feedback with `about` `storage`, giving the machine, command, error and workaround, then continue with the workaround.
