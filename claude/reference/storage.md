# Storage

These rules are part of the global instructions (`~/.claude/CLAUDE.md`, Storage section) and have the same force. Read them (and `~/.config/local/fleet-and-storage.md` when present) before you use `storagectl` or split work across machines.

- Keep work that another machine or a later session may read on the shared storage through `storagectl`, not only in a local folder: downloads, datasets, run outputs and handoff files. Start with `storagectl dests` to see which destinations are online, then use `put`, `get`, `ls`, `find`, `fetch <url> <dest>:<path>/` or `run --to <dest>:<path> -- <command>`. Host-specific destination catalogs and allocation docs live in `~/.config/local/fleet-and-storage.md` when present.
- Choose the destination by need: `cloud` (durable object storage) when the data must not depend on a Mac being awake; `pro` for large data, offline while the Pro sleeps; `air` (small) only for work in progress, never for an archive. Finished work that is kept (archives, parked task scratch, outputs of a closed study) goes to `cloud:archive/<repository name>/`, not to `air`; large data still goes to `pro`. A project rule against disclosure to external services does not forbid these destinations because they are your own storage. A project rule that keeps named material on one machine or out of third-party storage still applies, and credentials stay out. Check `~/.config/local/fleet-and-storage.md` (when present) for VPS destination limits and root-shell rules.
- Split work across machines when another one suits a step better: remote VPS pools for large downloads and cloud-heavy steps, the Pro for large data and long CPU jobs. Run such a step with `storagectl run --on <machine> --to <dest>:<path> [--stage <file or dir>] -- <command>`. It runs detached as that machine's `storage-runner` account and prints a job id; the command writes results to `$STORAGE_OUT`, which is sent to `--to` with the job's log, also when it fails. Follow it with `storagectl status|logs|cancel <id>` or `storagectl jobs --on <machine>`. Stage only small inputs (up to 1 GiB); pass larger ones through destinations, which the job reads with `storagectl` and the runner's own keys. Never run workloads as root on remote VPS hosts; check `~/.config/local/fleet-and-storage.md` for per-host limits.
- To run a full T3 thread on the Pro from the Air (while the Pro is awake), check `t3_environment_links` for its `environmentId`, then call `delegate_task` targeting that `environmentId` on `antigravity` (`gemini-4-neon`, omitting `isolation: "worktree"`) and exchange inputs and outputs through `storagectl`. To read threads on the other Mac, pass its `environmentId` to `t3_thread_list` or `t3_thread_read` (Air → Pro is `full-access`; Pro → Air is `read-only`). To check the Pro's `~/.config` commit read-only as the Pro's user, run `git -C ~/.config log -1` over SSH to the Pro host in `~/.ssh/config.d/` or in a Pro T3 thread (`storagectl run --on pro` runs as `storage-runner` and cannot read it). The Pro's providers, repositories and reach are in `~/.config/local/fleet-and-storage.md` when present.
- Report what got in the way as Feedback with `about` `storage`, giving the machine, command, error and workaround, then continue with the workaround.
