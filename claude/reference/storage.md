# Storage

These rules are part of the global instructions (`~/.claude/CLAUDE.md`, Storage section) and have the same force. Read them (and `~/.config/local/fleet-and-storage.md` when present) before you use `storagectl` or split work across machines.

- Keep work that another machine or a later session may read on the shared storage through `storagectl`, not only in a local folder: downloads, datasets, run outputs and handoff files. Start with `storagectl dests` to see which destinations are online, then use `put`, `get`, `ls`, `find`, `fetch <url> <dest>:<path>/` or `run --to <dest>:<path> -- <command>`. Host-specific destination catalogs and allocation docs live in `~/.config/local/fleet-and-storage.md` when present.
- Default to egress-free routing: `cloud` (`vps-storage-shared`, COS Tokyo) charges paid public outbound egress from Macs (¥0.46-0.75/GB), while Tailscale pools (`pro:`, `sai:`, `svps:`) are ¥0/GB and `sai` reaches COS Tokyo over Tencent's free internal endpoint (`169.254.0.47`, ¥0/GB). Choose the destination by need: use free Tailscale pools first — `pro` for large data, Mac-to-Mac transfers, working datasets and scratch/tmp staging (offline while the Pro sleeps) or `sai` (12 GiB, always up) when active/cross-Mac/temp files must not depend on a Mac being awake; `air` (small) only for work in progress, never for an archive. Never put disposable `tmp/` prefixes into versioned `cloud:` (deleted objects remain billed for 30 days as noncurrent versions). Reserve `cloud` (write-once, rarely-read durable object storage) for durable cold archives and small always-reachable handoffs: kept finished work (archives, outputs of a closed study) goes to `cloud:archive/<repository name>/`, not to `air`; large data still goes to `pro`. Always pack multi-file archives into `.tar.zst` + manifest before uploading to `cloud:archive/<repository name>/` (avoid tens of thousands of loose objects), and verify checksums locally or via `storagectl run --on sai` — never by downloading GBs back to a Mac. A project rule against disclosure to external services does not forbid these destinations because they are your own storage. A project rule that keeps named material on one machine or out of third-party storage still applies, and credentials stay out. Check `~/.config/local/fleet-and-storage.md` (when present) for VPS destination limits and root-shell rules.
- Split work across machines when another one suits a step better: remote VPS pools (`sai` for COS-heavy bulk reads, verification, repacking over free internal `169.254.0.47`, and large downloads), the Pro for large data and long CPU jobs. Run such a step with `storagectl run --on <machine> --to <dest>:<path> [--stage <file or dir>] -- <command>` (use `storagectl run --on sai` to offload `cloud:` reads, checks or repacks at ¥0/GB egress). It runs detached as that machine's `storage-runner` account and prints a job id; the command writes results to `$STORAGE_OUT`, which is sent to `--to` with the job's log, also when it fails. Follow it with `storagectl status|logs|cancel <id>` or `storagectl jobs --on <machine>`. Stage only small inputs (up to 1 GiB); pass larger ones through destinations, which the job reads with `storagectl` and the runner's own keys. Never run workloads as root on remote VPS hosts; check `~/.config/local/fleet-and-storage.md` for per-host limits.
- For restic verification, run `restic check --read-data` against Pro's local replica (`~/Library/Application Support/Sai Storage/replicas/...`, ¥0/GB) rather than against COS from a Mac; run metadata-only `restic check` against COS.
- To run a full T3 thread on the Pro from the Air (while the Pro is awake), check `t3_environment_links` for its `environmentId`, then call `delegate_task` targeting that `environmentId` on `antigravity` (`gemini-4-neon`, omitting `isolation: "worktree"`) and exchange inputs and outputs through `storagectl`. To read threads on the other Mac, pass its `environmentId` to `t3_thread_list` or `t3_thread_read` (Air → Pro is `full-access`; Pro → Air is `read-only`). To check the Pro's `~/.config` commit read-only as the Pro's user, run `git -C ~/.config log -1` over SSH to the Pro host in `~/.ssh/config.d/` or in a Pro T3 thread (`storagectl run --on pro` runs as `storage-runner` and cannot read it). The Pro's providers, repositories and reach are in `~/.config/local/fleet-and-storage.md` when present.
- Report what got in the way as Feedback with `about` `storage`, giving the machine, command, error and workaround, then continue with the workaround.
